## 1. 一页结论

Anime 已经完成了较完整的客户端—后端纵向切片：发现、搜索、条目详情、资料库、Bangumi 集成、评论、评分、社区动态、个人页和多端宿主均有代码或接口基础。当前问题不是“没有产品”，而是产品决策、客户端实现、独立后端和文档基线没有收敛到同一条发布主线。

截至本次盘点，项目不具备发布候选版本条件：客户端 `animeCheck` 未通过，后端 `fmt` 与 `clippy -D warnings` 未通过；客户端契约与后端实际 OpenAPI 存在两套版本，数据库迁移也存在两套事实源；截图测试、UI 测试和性能基准任务目前仍是入口占位。后端仓库另有用户未提交修改，本次整理未改动这些文件。

产品当前应从“功能继续堆叠”切换为“冻结发布范围、统一契约、打通核心闭环、补齐质量门禁”。

## 2. 产品定位与发布分层

### 2.1 不变的产品定位

Anime 是以动画条目为中心的资料、个人片库和公开社区发现产品，核心闭环为：

```text
发现/搜索 -> 查看条目 -> 收藏与记录进度 -> 评分/短评 -> 个人页与动态 -> 再发现
```

明确不做：视频播放或下载、私聊、广告和会员体系、复杂推荐平台、微服务拆分。

### 2.2 建议生效的发布分层

| 层级 | 目标 | 纳入内容 | 当前判断 |
|---|---|---|---|
| R0 Demo | 可重复演示与 UI 开发 | Fixture 驱动的发现、搜索、详情、资料库和视觉系统 | 基本具备，需保留确定性验收 |
| R1 iOS IPA 首发 | 首先验证核心用户价值 | 目录/搜索/详情、Anime 评分、短评/讨论、Bangumi OAuth/绑定、收藏与进度同步、Bangumi 来源评分、个人片库 | 作为首发生产候选；仅提供 IPA 侧载，不上架商店 |
| R1 Android 第二阶段 | 扩大核心用户覆盖 | 与 iOS 共享 R1 MVP 能力和后端，完成 Android 适配与回归 | 作为第二生产候选；质量与契约未达标 |
| Desktop/Web | 跨端预览与开发验证 | 复用 CMP 共享 UI 和 Remote Repository | 仅做预览测试，不承担 R1 发布验收 |
| R2 社区扩展 | 从最小互动闭环扩展为完整社区 | 长评、关注、反应、通知、片单、动态排序、复杂推荐 | R1 MVP 之后再逐项开放 |

平台范围必须这样表达：iOS IPA 是首发生产目标，允许用户自行侧载但暂不上架商店；Android 是第二生产目标；Desktop/Web 仅用于预览测试。iOS 和 Android 共同承担 R1 功能验收，Desktop/Web 不作为发布阻断平台。

### 2.3 认证策略说明

此前提到的 `OAuth-only` 是指“只能用 Bangumi OAuth 登录 Anime，不提供 Anime 自己的用户名/密码账号”。它描述的是登录身份来源，不限制 Anime 自己的评分、评论或片库能力。

已确认采用“双入口身份模型”：Anime 本地账号用于社区身份，Bangumi OAuth 作为可选绑定，仅在用户需要 Bangumi 收藏/进度双向同步时使用。两种方式最终都换成 Anime 自己的 access/refresh token；Bangumi Token 只保存在服务端。OAuth-only 不作为 R1 方案。

### 2.4 Anime 评分与评论 R1 MVP

Anime 自有评分和评论是 R1 的核心差异化能力，不再延后到 R2。R1 采用“评分 + 短评 + 讨论”最小闭环：

- 评分：每个用户对每部作品一条 1–10 分评分，可更新；公开评分计算 Anime 社区平均分、票数和分布；
- 短评：作品级公开内容，1–500 字，可标记剧透；
- 讨论：作品级内容，1–300 字，支持一层回复和剧透标记；
- 游客可读取公开内容，登录后才能写入、删除和举报；
- 服务端负责长度校验、幂等、频率限制、基础敏感词拦截和软删除；
- Bangumi 评分和 Anime 社区评分使用完全独立的字段、接口和聚合链；
- 长评、关注、点赞/收藏反应、通知、片单和复杂动态排序延后。

详细接口、数据表、客户端 Repository 边界和验收用例见 [`02-community-mvp-technical-plan.md`](02-community-mvp-technical-plan.md)。

### 4.1 契约治理规则

当前不能同时把主仓库和后端仓库都称为 API 事实源。建议采用以下目标规则：

- API 由一份共享的 OpenAPI 作为唯一规范源；主仓库 `contracts/openapi/` 作为产品契约入口，后端仓库的 OpenAPI 作为同步副本，CI 必须做字节或规范化 diff 校验。
- 后端仓库 `migrations/` 是数据库部署的可执行事实源；主仓库 `contracts/database/` 只保留与其同步的设计镜像，不得再单独演进。
- 任何 API 或数据库变更必须同时更新：OpenAPI/迁移、客户端映射、后端实现、测试、变更记录和本基线中的状态。
- 在契约收敛完成前，禁止把新增接口视为“已完成产品能力”。

## 6. 建议执行顺序

### W1：治理冻结

确认 R1 目标用户和四条核心路径：访客发现、本地账号登录、可选 Bangumi 绑定后的收藏/进度同步、公开社区读取。双入口认证决策已冻结，后续只允许通过 ADR 修改。

### W2：契约收敛

逐项比较主仓库 28 条路径与后端 45 条路径，优先处理认证、详情、收藏同步、评论/短评、评分、动态、通知和用户资料。随后统一响应包络、ID 命名、分页、错误码和版本号，再补跨仓库校验。

### W3：核心闭环

先修资料库 Repository 数据源分裂，再验证认证、收藏、进度、冲突、离线恢复和来源评分；同时完成 Anime 评分、短评和讨论的 R1 MVP。社区长评、关注、反应、通知和片单仍由 R2 管理。

### W4：发布候选

完成客户端与后端质量门禁、真实 API 回归、截图和 UI 流程、无障碍、性能、崩溃/请求观测、迁移演练、备份恢复演练和 Android 发布包验收。所有结果附日期、环境和提交号。

## 8. 指标与发布判断

以下是 R1 的建议指标，当前仓库尚未证明已完成埋点，暂作为产品目标而不是现状数据：

- 激活：新用户 7 天内完成至少 3 个收藏，并完成 1 次进度或评分操作。
- 核心转化：发现/搜索到详情、详情到收藏、收藏到同步成功分别可观测。
- 稳定性：同步成功率、API 5xx、登录失败、离线恢复失败和崩溃率按版本统计。
- 社区质量：举报处理时效、删除/撤回成功率、重复提交率和敏感内容拦截率。
- 留存：D1、D7 留存与“完成一次核心闭环”的用户分组比较。

发布结论只有三种：`未开始`、`可进入验收`、`可发布`。当前各产品域最多只能标为“可进入验收”，整个项目仍为“未达到可发布”。
