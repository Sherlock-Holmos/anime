# Anime 社区评分与评论 R1 最小 MVP 技术方案

> 文档编号：`COMMUNITY-MVP-2026-09`  
> 整理日期：`2026-09-13`  
> 适用版本：R1 iOS IPA 首发、R1 Android 第二阶段  
> 状态：产品方案已确认，作为 R1 实现合同

## 1. MVP 目标

Anime 的差异化不是单纯的动漫资料查询，而是“看资料、留下判断、与其他用户交流”。R1 社区 MVP 只解决一条稳定闭环：

```text
查看作品 -> 给出 Anime 评分 -> 写一条短评或讨论 -> 其他人阅读 -> 回到作品详情
```

发布顺序为：iOS IPA 侧载首发，Android 随后作为第二生产目标；Desktop 和 Web 只承担预览、接口联调和回归测试，不作为 R1 发布验收平台。

## 2. R1 MVP 范围

### 2.1 必须完成

| 能力 | MVP 规则 |
|---|---|
| Anime 个人评分 | 登录用户对一个作品维护一条 1–10 分评分，可重复提交并更新 |
| Anime 社区评分 | 只聚合公开 Anime 评分，展示平均分、票数和分布；与 Bangumi 评分完全分离 |
| 短评 | 作品级公开短评，1–500 字，无标题；可标记剧透 |
| 讨论 | 作品级讨论，1–300 字；支持顶层讨论和一层回复，可标记剧透 |
| 内容读取 | 游客可以读取公开评分、短评和讨论；写入、编辑、删除、举报需要登录 |
| 基础治理 | 服务端长度校验、频率限制、基础敏感词拦截、用户删除自己的内容、举报入队 |
| 跨端体验 | iOS 与 Android 共享领域模型、Repository、接口和 Compose 页面；平台只负责会话/存储适配 |

### 2.2 不进入 R1 首发阻断项

长评、点赞/收藏反应、关注关系、动态排序、通知中心、片单创建、复杂推荐、评论全文搜索和运营后台 UI。后端可以保留已有接口，但客户端入口由产品范围或功能开关控制，避免 MVP 同时承担完整社交平台的复杂度。

## 3. 认证方案说明

### 3.1 OAuth-only 是什么

OAuth-only 的意思是：用户只能通过 Bangumi OAuth 登录 Anime，Anime 不提供自己的用户名/密码注册和登录。Bangumi 负责确认用户身份，Anime 保存映射关系和自己的会话；用户的 Bangumi Token 只保存在服务端。

这不是“所有 API 都必须调用 Bangumi”，也不代表 Anime 不能有自己的评分、评论和片库；它只描述登录身份来源。

### 3.2 R1 已确认方案

R1 采用“双入口身份模型”：

1. Anime 本地账号是社区身份，可直接用于浏览、评分、短评和讨论；
2. Bangumi OAuth 是可选绑定，用于读取和双向同步 Bangumi 收藏/进度；
3. 一个 Anime 账号最多绑定一个 Bangumi 账号；解绑前必须明确同步数据的保留规则；
4. 两种登录方式最终都换成 Anime 自己的短期 access token + 可轮换 refresh token，客户端不直接保存 Bangumi Token。

该模型基于当前后端已有本地账号和 Bangumi OAuth 两条实现链路，现已由产品确认。后续不得再把 OAuth-only 作为默认方案；如需改变身份模型，必须新增 ADR 并同步客户端、后端和隐私说明。

## 4. 领域与数据方案

### 4.1 评分

作品以 Bangumi `subject_id` 作为 API 外部标识，数据库内部使用自己的 `subjects.id`。评分采用以下两张表：

- `user_ratings`：`(user_id, subject_id)` 唯一；保存 `score`、标签、可见性和更新时间；
- `community_rating_aggregates`：保存公开评分的平均分、票数、1–10 分布和更新时间，是可重建的派生快照。

写入评分时在同一事务中完成：校验 → Upsert 用户评分 → 重建该作品公开聚合 → 写入活动记录。Bangumi 的 `score/votes/distribution` 只写入作品镜像，不能参与 Anime 聚合。

### 4.2 短评与讨论

- `reviews` 表保存短评；R1 只允许 `kind=short`，正文 1–500 字；
- `subject_comments` 表保存讨论，正文 1–300 字，`parent_id` 只允许指向同一作品的顶层讨论；
- 正文、剧透标志、作者、创建/编辑/删除状态和可见性由服务端控制；客户端只负责编辑体验；
- 删除采用软删除或内容替换，保留最小审计信息，避免动态和举报记录失去关联。

## 5. API 与客户端边界

### 5.1 R1 API

| 方法 | 路径 | 权限 | 作用 |
|---|---|---|---|
| GET | `/subjects/{subject_id}` | 游客 | 返回 `anime_rating` 与 `bangumi_rating` 两个独立对象 |
| GET | `/subjects/{subject_id}/community-rating` | 游客 | 返回 Anime 聚合评分 |
| PUT | `/me/ratings/{subject_id}` | 登录 | 新增或更新个人评分，要求幂等 |
| GET | `/subjects/{subject_id}/reviews` | 游客 | 分页读取公开短评 |
| POST | `/subjects/{subject_id}/reviews` | 登录 | 发布短评 |
| GET | `/subjects/{subject_id}/comments` | 游客 | 分页读取公开讨论 |
| POST | `/subjects/{subject_id}/comments` | 登录 | 发布讨论或一层回复 |
| PATCH/DELETE | `/reviews/{review_id}`、`/comments/{comment_id}` | 作者 | 编辑或删除自己的内容 |
| POST | `/comments/{comment_id}/reports` | 登录 | 举报讨论 |

当前后端已经有大部分上述路由和表，但主仓库与独立后端的参数命名、响应包络、版本号仍有差异。R1 开发必须先完成一份共享 OpenAPI，再把客户端 Remote Repository 和后端实现按同一份契约回归。

### 5.2 客户端状态边界

- `SubjectViewModel` 负责作品资料与社区摘要的加载，不把社区错误升级为作品资料错误；
- `CommunityRepository` 负责评分、短评、动态等社区 API；`CommentRepository` 负责讨论列表、草稿和讨论写操作；
- 评分可以使用已有 `OfflineFirstCommunityRepository` 和 Rating Outbox：离线时保存最后一次评分意图，恢复网络后重试；
- 讨论和短评先采用 online-first 写入，但必须保存本地草稿，发布失败不能清空正文；
- 服务端返回成功对象后，客户端更新当前页面或触发一次精确刷新，不依赖“重新打开页面”才能看到结果；
- 评分与短评/讨论是两个独立写操作。评分成功、正文失败时必须明确提示“评分已保存，内容发布失败”，不能伪装成整个操作原子成功。

## 6. 基础治理与安全

R1 不建设复杂审核平台，但必须具备最低安全闭环：

- 服务端按 Unicode 字符数限制长度，客户端限制只是体验优化；
- 评分写入按用户和作品 Upsert，不能因为重复点击制造重复票；
- 短评/讨论写入使用 `Idempotency-Key`，网络重试不得生成重复内容；
- 同一用户限制短时间内的发布次数，并拦截已知垃圾广告词；
- 默认公开内容可被游客读取；私密/仅关注者可见性若缺少完整读取规则，不在 R1 UI 暴露；
- 举报记录进入可审计状态流；作者删除后正文不可继续公开展示；
- access token、refresh token、Bangumi Token、评论正文不得写入日志或 URL。

## 7. R1 验收用例

1. 游客打开作品详情，可以同时看到 Bangumi 评分和 Anime 社区评分，且来源标签、票数和更新时间清晰。
2. 登录用户提交 1–10 分评分，刷新页面后仍存在；再次提交只更新原记录，社区平均分和票数正确变化。
3. 登录用户发布 1–500 字短评，短评出现在作品详情和短评列表；重复请求不会产生两条记录。
4. 登录用户发布 1–300 字讨论，并能回复一条顶层讨论；超过一层时服务端拒绝。
5. 讨论和短评的剧透内容默认折叠；删除后正文不再公开显示。
6. 游客可以阅读但不能发布；未登录点击写入动作进入登录流程，登录成功后回到原作品和原动作。
7. 断网时评分进入 Outbox，恢复网络后自动重试；短评/讨论发布失败时草稿仍在。
8. 社区 API 失败时，作品基础资料、章节、角色和 Bangumi 评分仍可正常查看。
9. iOS IPA 与 Android 在同一后端环境完成以上用例；Desktop/Web 只做预览和接口回归，不作为首发阻断项。

## 8. 当前实现差距与工作包

当前仓库已经具备评分表、聚合计算、短评/讨论路由、基础治理、Remote Repository、iOS 存储适配和大部分页面。R1 仍需完成：

| 工作包 | 结果 |
|---|---|
| C0 产品与认证确认 | ✅ 已完成：采用 Anime 本地账号 + 可选 Bangumi OAuth 绑定 |
| C1 契约收敛 | 统一主仓库/后端 OpenAPI 的路径、ID、响应、错误码和幂等语义 |
| C2 评分闭环 | 详情页展示、评分入口、聚合刷新、Outbox 重试和部分失败提示 |
| C3 评论闭环 | 游客读取、登录写入、草稿恢复、分页、一层回复、删除和举报 |
| C4 真实环境验收 | PostgreSQL migration、iOS IPA、Android 真机/模拟器、社区 E2E |
| C5 发布门禁 | 修复客户端 ktlint、后端 fmt/clippy，并补齐截图/UI/性能证据 |

R1 MVP 的完成定义不是“代码里存在接口”，而是上述验收用例在 iOS 和 Android 的真实后端环境均能通过，并且契约、迁移、日志和失败恢复行为一致。
